# Task Management API

REST API для управления задачами, разработанный на Java 21 с использованием Spring Boot, Spring Web, Spring Data JPA и PostgreSQL.

Проект демонстрирует многоуровневую архитектуру приложения, использование DTO для обработки запросов и ответов, валидацию данных, централизованную обработку исключений, а также автоматизированное тестирование сервисного и веб-слоёв.

## Возможности

- Получение списка всех задач.
- Получение отдельной задачи по ID.
- Создание новых задач.
- Полное обновление редактируемых полей задачи с помощью `PUT`.
- Частичное обновление задачи с помощью `PATCH`.
- Удаление задач.
- Валидация входящих запросов с помощью Jakarta Bean Validation.
- Обработка ошибок при отсутствии задачи и некорректных запросах.
- Тестирование сервисного слоя и контроллеров с помощью JUnit, Mockito и MockMvc.

## Архитектура приложения

Приложение использует многоуровневую архитектуру:

- **Controller** — предоставляет REST-эндпоинты и обрабатывает HTTP-запросы.
- **Service** — реализует бизнес-логику работы с задачами и преобразует сущности в DTO ответов.
- **Repository** — обеспечивает доступ к базе данных с помощью Spring Data JPA.
- **Entity** — представляет задачу в базе данных.
- **DTO** — определяет структуру входящих запросов и исходящих ответов.
- **Глобальный обработчик исключений** — преобразует поддерживаемые исключения в HTTP-ответы с информацией об ошибке.

Основная сущность предметной области — `Task`. Она содержит идентификатор, заголовок и описание и сопоставляется с таблицей `task` в базе данных.

## API

Все эндпоинты используют базовый путь `/tasks`.

| Метод | Эндпоинт | Описание | Успешный ответ |
|---|---|---|---|
| `GET` | `/tasks` | Получить все задачи | `200 OK` |
| `GET` | `/tasks/{id}` | Получить задачу по ID | `200 OK` |
| `POST` | `/tasks` | Создать задачу | `201 Created` |
| `PUT` | `/tasks/{id}` | Обновить редактируемые поля задачи | `200 OK` |
| `PATCH` | `/tasks/{id}` | Частично обновить задачу | `200 OK` |
| `DELETE` | `/tasks/{id}` | Удалить задачу | `204 No Content` |

Если задача, необходимая для выполнения операции, не существует, API возвращает `404 Not Found`.

### Структура задачи

Ответ с информацией о задаче имеет следующий формат:

```json
{
  "id": 1,
  "title": "Подготовка к собеседованию по Java",
  "description": "Повторить Java, Spring, JPA и тестирование"
}
```

Поле `id` генерируется на уровне слоя хранения данных.

### Создание задачи

**Запрос**

```http
POST /tasks
Content-Type: application/json
```

```json
{
  "title": "Прочитать Effective Java",
  "description": "Изучить выбранные главы"
}
```

**Пример с использованием cURL**

```bash
curl -i -X POST http://localhost:8080/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Прочитать Effective Java",
    "description": "Изучить выбранные главы"
  }'
```

При успешном выполнении возвращается `201 Created` и JSON с созданной задачей.

### Получение списка задач

```bash
curl -i http://localhost:8080/tasks
```

Возвращается `200 OK` и JSON-массив задач. Если задач нет, ответ содержит пустой массив.

### Получение задачи по ID

```bash
curl -i http://localhost:8080/tasks/1
```

Если задача существует, возвращается `200 OK`. Если задача не найдена, возвращается `404 Not Found`.

### Полное обновление задачи

Метод `PUT` обновляет заголовок и описание задачи на основе переданного тела запроса.

```http
PUT /tasks/1
Content-Type: application/json
```

```json
{
  "title": "Прочитать Spring in Action",
  "description": "Изучить разработку приложений на Spring"
}
```

В запросе следует передавать оба поля. Для него применяются те же правила валидации DTO, что и при создании задачи.

### Частичное обновление задачи

Метод `PATCH` обновляет только те поля, которые переданы со значениями, отличными от `null`.

```http
PATCH /tasks/1
Content-Type: application/json
```

```json
{
  "description": "Повторить главу о работе с данными"
}
```

В этом примере обновляется описание, а существующий заголовок сохраняется.

**Текущее поведение:** отсутствующие поля и поля, явно переданные со значением JSON `null`, обрабатываются одинаково — как поля, которые не нужно обновлять. Пустой PATCH-запрос в текущей реализации явно не отклоняется.

### Удаление задачи

```bash
curl -i -X DELETE http://localhost:8080/tasks/1
```

При успешном удалении возвращается `204 No Content` без тела ответа.

## Валидация и обработка ошибок

Валидация запросов применяется к эндпоинтам создания, полного обновления и частичного обновления задачи.

Текущие правила валидации:

- `TaskRequestDto.title` не может быть пустым или состоять только из пробельных символов.
- Длина `TaskRequestDto.title` не должна превышать 255 символов.
- Поле `TaskPatchRequestDto.title`, если оно передано, не должно превышать 255 символов.
- Для поля `description` в текущих DTO не определены явные ограничения Bean Validation.

Таким образом, пустой заголовок недопустим в запросах `POST` и `PUT`. Для заголовка в `TaskPatchRequestDto` ограничение `@NotBlank` в текущей реализации не применяется.

### HTTP-коды ответов

| Код | Значение |
|---|---|
| `200 OK` | Запрос успешно выполнен |
| `201 Created` | Задача создана |
| `204 No Content` | Задача удалена |
| `400 Bad Request` | Ошибка валидации запроса |
| `404 Not Found` | Запрашиваемая задача не найдена |

Глобальный обработчик исключений обрабатывает ошибки отсутствующей задачи и ошибки валидации запросов. Формат ответа зависит от типа исключения, поэтому в текущей реализации структуры ошибок не полностью унифицированы.

Пример ответа при ошибке валидации:

```json
{
  "timestamp": "2026-01-01T12:00:00",
  "status": 400,
  "error": "Validation Error",
  "errors": {
    "title": "must not be blank"
  }
}
```

Значение `timestamp` приведено для примера. В реальном ответе указывается время возникновения ошибки.

## Настройка базы данных

Приложение использует PostgreSQL. Параметры подключения задаются в файле:

`src/main/resources/application.properties`

Пример конфигурации:

```properties
spring.application.name=task-management-api

spring.datasource.url=jdbc:postgresql://localhost:5432/task_management
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

Перед запуском убедитесь, что:

1. PostgreSQL установлен и запущен.
2. Создана база данных `task_management`.
3. Переменные окружения `DB_USERNAME` и `DB_PASSWORD` содержат имя пользователя и пароль базы данных.

Приведённая конфигурация предназначена для примера локального запуска. При необходимости измените имя базы данных, URL и параметры подключения.

**Важно для production:** текущая конфигурация использует режим Hibernate `update` для обновления схемы базы данных и включает вывод SQL-запросов в журнал. Перед развёртыванием в production рекомендуется пересмотреть эти настройки. Для контролируемого управления изменениями схемы можно использовать Flyway или Liquibase.

Не добавляйте реальные пароли и другие секретные данные в систему контроля версий.

## Запуск проекта

### Требования

Перед запуском установите:

- JDK 21;
- Maven;
- PostgreSQL.

### 1. Клонирование репозитория

Замените URL и имя каталога на фактические значения вашего GitHub-репозитория.

```bash
git clone https://github.com/GeorgeLevchuk/task-management-api.git
cd task-management-api
```

### 2. Настройка PostgreSQL

Создайте базу данных и настройте параметры подключения в файле `src/main/resources/application.properties`.

Установите переменные окружения, используемые конфигурацией:

```bash
export DB_USERNAME=your_database_username
export DB_PASSWORD=your_database_password
```

Эти команды предназначены для Linux и macOS. В Windows задайте аналогичные переменные окружения через используемую оболочку или IDE.

### 3. Запуск приложения

Выполните из корневого каталога проекта:

```bash
mvn spring-boot:run
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8080
```

Например, получить список задач можно командой:

```bash
curl http://localhost:8080/tasks
```

## Запуск тестов

Для запуска тестового набора выполните:

```bash
mvn test
```

В проекте предусмотрены следующие тесты:

- **`TaskServiceTest`** — модульные тесты операций сервиса задач с использованием Mockito.
- **`TaskControllerTest`** — тесты контроллера с использованием Spring MVC Test и MockMvc.
- **`TaskManagementApiApplicationTests`** — тест загрузки контекста приложения.

Чтобы запустить отдельный класс тестов:

```bash
mvn -Dtest=TaskServiceTest test
```

Тесты контроллера охватывают отдельные сценарии GET и POST. Отдельные тесты контроллера для всех сценариев PUT, PATCH и DELETE в текущей версии проекта не предусмотрены.

Результаты тестирования зависят от конфигурации и окружения. Выполните указанные команды самостоятельно, чтобы проверить сборку и тесты в своей среде.
